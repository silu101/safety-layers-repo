# Known Discrepancies: Paper Text vs. Shipped Repo

Found while building the reproduction spec by reading the actual code in
https://github.com/listen0425/Safety-Layers rather than relying on the paper's
prose. Log new ones here as you find them — this is exactly the kind of thing
the project's "Reproduction" phase is meant to surface.

| # | Discrepancy | Paper says | Code/data shows | Status / action |
|---|---|---|---|---|
| 1 | Over-rejection dataset size | "721 problems" (Table 1 caption, Appendix A.3.4) | `Dataset/Evaluation/Over_rejection_dataset.csv` has 731 rows | Not yet resolved. Could be a dataset version update since publication, or a paper typo. Check before running Section 3.4 localization; if reproducing Table 1's exact numbers, may need to find/reconstruct the 721-row version, or accept a small offset and note it. |
| 2 | `normal.csv` query count | Paper states P=100 (Section 3.2, Fig. 1 caption) | `Code/Cos_sim_analysis/normal.csv` has 99 rows | Check whether a header row is being silently dropped somewhere in the authors' pipeline, or whether this is a genuine 1-row discrepancy. Low impact on results (r=500 draws with replacement-ish sampling across pairs), but worth resolving for an exact match. |
| 3 | Shipped reference `all_cos.pkl` | Paper's r=500 for the cosine similarity analysis | The file at `Code/Cos_sim_analysis/cos_sims/all_cos.pkl` in the original repo (copied here as `reference/all_cos_phi3_authors.pkl`) has only **10 draws per pair-type** | Almost certainly a demo/smoke-test artifact left in the repo, not the authors' full r=500 result used to generate Fig. 1. Treat as a pipeline sanity check only — `compare.py` emits an explicit warning when comparing against small-r data. Do not use it to validate the paper's exact numeric claims. |
| 4 | Model-specific code branches | Not mentioned as needing manual edits | `Attention_scores/att_scores.py` requires uncommenting lines 51/85 for Gemma models; `Safety_layers_locating/scaling.py` requires swapping `scaling()` → `scaling_phi3()` for Phi-3 models (different attention/MLP module names: `q_proj/k_proj/v_proj` vs. fused `qkv_proj`) | Only relevant once Section 3.4/3.6 modules are ported (see README "Scope"). Note here now so it's not missed later. |
| 5 | `Backdoor_dataset.json` naming vs. paper's DI/DB taxonomy | Paper defines DN (normal), DI (implicit attack: no trigger, "Sure, the answer is:" prefix), DB (backdoor: has a trigger phrase + same prefix), with DI having 4000 entries and DB being a 1:1 mix of backdoor:normal | The shipped `Dataset/Finetune/Backdoor_dataset.json` (4000 entries) reads as the **implicit**-style data (no trigger keyword) by the paper's own definition, not backdoor-style | Only relevant once Section 4 (SPPFT) is ported. | 6 | `Full_finetuning.py` vs `SPPFT.py` default learning rates | Appendix Table 6 gives one LR per model (e.g. Llama-2-7b-chat: `3e-4`) | Script defaults differ from each other (`Full_finetuning.py` default `3e-4`, `SPPFT.py` default `3e-5`) and neither is guaranteed to match Table 6 for every model | Only relevant once Section 4 is ported. Always pass `--learning_rate` explicitly from Table 6 rather than trusting either script's default. |

| 7 | `configs/phi3_cossim.yaml` checked-in `dtype` | Intended as fidelity-matched `float32` per project discussion (Phi-3 float32 matches the authors' precision exactly) | File shipped with `dtype: auto` (also the `CosSimConfig` dataclass default in `config.py`) | Resolved 2026-08-18: corrected `configs/phi3_cossim.yaml` to `dtype: float32`. `configs/phi3_cossim_smoketest.yaml` intentionally left at `dtype: auto` since it's a pipeline sanity check, not a fidelity target. If a full run OOMs on 16GB VRAM (float32 Phi-3 needs ~15-20GB), the fallback is a runtime `--set dtype=auto` override, not a further config edit — see REPLICATION_LOG.md for whether this was needed. |

| 8 | `trust_remote_code` setting for Phi-3 | Original script (and this repo's configs, until 2026-08-19) set `trust_remote_code: true`, matching `save_all_pairs_cos_sim.py` | On Kaggle's GPU environment (`transformers==5.0.0`), `trust_remote_code=True` always fetches the *latest*, unpinned custom modeling code from `microsoft/Phi-3-mini-4k-instruct` on the HF Hub. That remote code's `_init_rope()` does `self.config.rope_scaling["type"]`, which `KeyError`s against how `transformers==5.0.0` now loads/normalizes `rope_scaling` -- a version-drift incompatibility between the always-latest remote code and a very new `transformers`, not a bug in this repo. | Resolved 2026-08-19 (deviation, not a fix-in-place): switched both `configs/phi3_cossim.yaml` and `configs/phi3_cossim_smoketest.yaml`, plus the `CosSimConfig` dataclass default, to `trust_remote_code: false`. This uses `transformers`' own built-in, version-matched Phi-3 implementation instead of Microsoft's custom remote code. **This is a fidelity deviation from the original authors' script**, not guaranteed to be numerically identical to their custom code path (e.g. attention/MLP module naming differs -- see discrepancy #4). Note this explicitly wherever `configs/phi3_cossim.yaml` results are cited in `docs/REPLICATION_LOG.md`. The alternative (pinning `transformers` to an older version compatible with the remote code, keeping `trust_remote_code: true`) was considered and rejected for now in favor of unblocking the run quickly; revisit if the native-vs-remote-code numeric difference turns out to matter for the reproduction claim. |

| 9 | Kaggle free-tier GPU assignment | N/A -- not a paper/authors' repo discrepancy, an execution-environment one | Kaggle's free-tier GPU pool can assign an old Tesla P100 (Pascal, compute capability 6.0) instead of a T4. Kaggle's preinstalled torch build (as of 2026-08-19, `torch==2.10.0+cu128`) is compiled only for `sm_70+`, so it can't run at all on a P100 (`CUDA error: no kernel image is available for execution on the device`). Confirmed via 4 consecutive kernel runs all assigned P100; neither the classic API push path (`kernel-metadata.json` has no accelerator-selection field in the client we can currently authenticate with) nor manually setting "GPU T4 x2" in the Kaggle web UI (doesn't survive a subsequent API push) could force T4. This is a known, still-open Kaggle-side bug (`Kaggle/docker-python#1546`) with no official fix as of this writing. | Resolved 2026-08-19 (environment workaround, not a config change): `kaggle/kernel_runner.py`'s `ensure_gpu_compatible_torch()` checks the assigned GPU's compute capability via `nvidia-smi` before importing torch, and if it's < 7.0, reinstalls `torch==2.7.1+cu118` (the newest PyTorch release that still ships `sm_60` kernels; 2.8+ dropped Pascal support entirely). This is itself a deviation from Kaggle's standard preinstalled environment -- note it in `docs/REPLICATION_LOG.md` whenever it triggers, and be aware a much older torch paired with the newer preinstalled `transformers` could introduce its own compatibility issues (untested combination). |

| 10 | `num_beams` in the cosine-similarity generation | `docs/REPRODUCTION_SPEC.md` (and this repo's code, until 2026-08-23) treated `num_beams=4` as load-bearing, per the original script's `get_output(..., num_beams=4, ...)` signature and the paper's stated generation params | The original script's `get_output()` in `Code/Cos_sim_analysis/save_all_pairs_cos_sim.py` never forwards `num_beams` into `GenerationConfig(...)` or `model.generate()` -- only `temperature`, `top_p`, `top_k`, `pad_token_id` are set. This is a bug in the authors' own code: their real executed behavior is `num_beams=1` (the default), and since `do_sample` is never set either, HF's `generate()` falls back to plain greedy decoding -- `temperature`/`top_p`/`top_k` are silently inert. Confirmed by comparing our reproduced Phi-3 curve against the actual published Fig. 1: ours showed a ~7-10 degree N-M vs N-N angular-difference plateau where the real figure shows ~40-50 degrees, a 4-5x gap far beyond expected environment noise -- our `cos_sim.py` had been correctly implementing genuine 4-beam beam search, which is NOT what generated the paper's real numbers. | Resolved 2026-08-23: removed `num_beams` from the `GenerationConfig` in `get_last_position_hidden_states()` (`cos_sim.py`), so generation now defaults to `num_beams=1`/greedy, matching the original script's actual (buggy) executed behavior rather than its apparent documented intent. `cfg.num_beams` still exists in `CosSimConfig`/configs as a record of the original parameter name but is no longer applied. Re-running Phi-3 to confirm this closes the gap against the published figure -- see `docs/REPLICATION_LOG.md`. |
