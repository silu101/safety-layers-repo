| 10 | `num_beams` in the cosine-similarity generation | `docs/REPRODUCTION_SPEC.md` (and this repo's code, until 2026-08-23) treated `num_beams=4` as load-bearing, per the original script's `get_output(..., num_beams=4, ...)` signature and the paper's stated generation params | The original script's `get_output()` in `Code/Cos_sim_analysis/save_all_pairs_cos_sim.py` never forwards `num_beams` into `GenerationConfig(...)` or `model.generate()` -- only `temperature`, `top_p`, `top_k`, `pad_token_id` are set. This is a bug in the authors' own code: their real executed behavior is `num_beams=1` (the default), and since `do_sample` is never set either, HF's `generate()` falls back to plain greedy decoding -- `temperature`/`top_p`/`top_k` are silently inert. Confirmed by comparing our reproduced Phi-3 curve against the actual published Fig. 1: ours showed a ~7-10 degree N-M vs N-N angular-difference plateau where the real figure shows ~40-50 degrees, a 4-5x gap far beyond expected environment noise -- our `cos_sim.py` had been correctly implementing genuine 4-beam beam search, which is NOT what generated the paper's real numbers. | Resolved 2026-08-23: removed `num_beams` from the `GenerationConfig` in `get_last_position_hidden_states()` (`cos_sim.py`), so generation now defaults to `num_beams=1`/greedy, matching the original script's actual (buggy) executed behavior rather than its apparent documented intent. `cfg.num_beams` still exists in `CosSimConfig`/configs as a record of the original parameter name but is no longer applied. Re-running Phi-3 to confirm this closes the gap against the published figure -- see `docs/REPLICATION_LOG.md`. |

| 11 | Section 3.4 over-rejection scoring methodology | Table 1 presents precise per-model safety-layer ranges, derived from over-rejection rate changes under weight scaling | `Code/Safety_layers_locating/scaling.py` only generates raw text responses to a CSV -- no scoring/classification code exists in the repo, and the paper's main text never states an explicit matching algorithm. However, the paper text is more constraining than "unspecified": Appendix A.3.3 says rejection templates appear "at the beginning of its response," and Section 3.4.3 says the model "explicitly express[es] this propensity at the start of their response," needing only the first 4-8 generated tokens -- i.e. a PREFIX-match design against a small per-model template set, not a substring-anywhere check. Three attempts tried and superseded: (a) prefix-match against Appendix A.3.3's 1-2 verbatim templates per model -- too narrow, undercounted refusals ~30x on real gemma-2b outputs; (b) an ad-hoc broadened keyword list -- not principled/citable, rejected per explicit instruction to avoid inventing our own heuristic; (c) Zou et al. 2023's `make_checking_fn()` substring-anywhere keyword list -- reverted, since that tool scores full jailbreak-attack completions (a different task) and doesn't match this paper's own "prefix, first few tokens" description. | Resolved 2026-08-23 (second revision): `refusal_classifier.py` keeps the paper's described PREFIX-match design (case-insensitive, start-of-response only) but broadens each model's template list beyond Appendix A.3.3's 1-2 examples with plausible same-style paraphrases, to address the undercount without abandoning the paper's own matching philosophy. The broadened template list itself is OUR OWN addition, not recovered from the paper or authors -- still emailed the authors 2026-08-23 for their actual list; revisit if they reply with something different. Re-run the Section 3.4 gemma sweep with this classifier -- see `docs/REPLICATION_LOG.md`. |
