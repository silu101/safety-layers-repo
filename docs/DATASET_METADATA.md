## Part 2 — Prompt-level schema (what to store per prompt in your own metadata CSV/JSON)

This is the schema this project's own pipeline already writes per pool record
(`sagemaker/entrypoint_ood_pipeline.py`'s pool-record construction) — use it as
your baseline column set:

| Field | Type | Meaning |
|---|---|---|
| `candidate` | string | The prompt text itself |
| `dataset` | string | Source dataset name (e.g. `"BeaverTails"`, `"Aegis"`, `"AdvBench"`) |
| `source_label` | string | Original category/tag from that dataset (dataset-specific — see Part 1's taxonomy row) |
| `similarity_to_advbench` | float | Cosine similarity (embedding-based) to nearest AdvBench prompt |
| `matched_advbench_prompt` | string | Which AdvBench prompt produced that nearest-neighbor score |
| `ambiguous_label` | bool | Whether this exact prompt text carries an inconsistent safety verdict elsewhere in its own source dataset (BeaverTails/Aegis only — see Part 1) |
| `id` (implicit, per record) | string | A stable short hash, used for manual override tracking in the curation tool |
| method-specific: `run_positive_control` inclusion, `exclude_from_candidates` flag | bool | Whether this record's source dataset is excluded as ID-contaminated for a given method (per `METHOD_CONFIGS`) |

**Not currently stored but worth adding**, given Parts 3-4 below:
- A linguistic-form tag (imperative instruction vs. question vs. role-play/jailbreak-wrapped vs. conversational) — none of the 8 sources tag this natively; it would need to be inferred (e.g. regex/heuristic on sentence form) since none of the papers/cards provide it.
- Prompt length (token or character count) — not stored today; cheap to add, not yet done.
- Multi-turn vs. single-turn flag — most sources are single-turn already; Anthropic Red Team is the one exception, and this project already collapses it to `task_description` at load time, so the flag would always read "single-turn" for what's actually in the pool today. Worth recording explicitly rather than leaving implicit.

**Positive-control grounding**: The 0.508 cosine-similarity number between
AdvBench and HarmBench (the pair the field already treats as "known partial
overlap") is the only empirically anchored reference point in this table. It
means even a genuinely-related, same-purpose benchmark barely reaches ~0.5
similarity to AdvBench — so any candidate category scoring meaningfully lower
than that (the 5 confirmed-OOD categories in this project's pool all sit
below the 0.5 threshold, with `hate_discrimination` further tuned to 0.28)
has a real empirical basis for the "OOD" label, not just a name-based one.

## Part 5 — What not to mix

- **Don't combine HarmBench's copyright behaviors with any "harm severity" claim** — copyright infringement is a categorically different kind of policy violation (IP, not safety/violence), and mixing it into an aggregate R_h number would conflate two different constructs the paper (and this project) should keep separate.
- **Don't treat Anthropic Red Team's `task_description` reduction as equivalent to its native multi-turn transcripts** — a model refusing a one-line summary of an attack goal is not the same test as a model navigating an actual multi-turn manipulation attempt. If a reviewer asks "did you test multi-turn robustness," the honest answer is no — this project only tests the single-turn summary proxy.
- **Don't pool MaliciousInstruct into a Safety Layers OOD set while also using it as `refusal_direction`'s ID data** — per `METHOD_CONFIGS`, MaliciousInstruct is method-relative ID/excluded for `refusal_direction`; if Safety Layers work ever adds MaliciousInstruct as an OOD source, that's fine (Safety Layers' own ID is AdvBench-only), but the two methods' pools must stay separately configured, which is exactly why `METHOD_CONFIGS` exists.
- **Don't mix BeaverTails/Aegis prompts flagged `ambiguous_label=True` into the main OOD pool without stratifying** — per the "Option A" decision already implemented in `scripts/analyze_ood_eval_result.py`, these need separate R_h/S_h reporting, not silent inclusion in one combined number, because they don't unambiguously deserve refusal the way every AdvBench/malicious.csv prompt does.
- **Don't compare SimpleSafetyTests results as if they were a stress test** — given its weak semantic/adversarial OOD-ness (Part 4), a model performing well on SimpleSafetyTests says little beyond what AdvBench itself already establishes; using it to claim "generalizes to OOD" would overstate what the dataset differs on.
